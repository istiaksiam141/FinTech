# Financial algorithms

## Exchange rate

The planner expects `1 unit of destination currency = rate BDT` (for example, BDT per GBP). The rate can be entered manually with a source and timestamp, or fetched on request as an indicative reference. Tuition cost in BDT is:

`tuition × BDT-per-destination-currency rate`

Manually entered rate timestamps must be valid local `YYYY-MM-DDTHH:mm` values and cannot be in the future. Manual rates remain user-provided and unverified. There is no age-based rejection policy for manual rates; students should confirm that the entered quote is still current. Fetched-rate freshness rules are described separately below.

### Bangladesh Bank published rates

The Vercel function `GET /api/exchange-rates` fetches the official [Bangladesh Bank exchange-rate sheet](https://www.bb.org.bd/en/index.php/econdata/exchangerate) server-side. The official page currently presents a dated HTML table and links to date-specific XLS and PDF files. On 13 October 2026, the linked files were `https://www.bb.org.bd/econdata/exchange_rate/exchange_rate_13_10_2026.xls` (XLS) and `https://www.bb.org.bd/econdata/exchange_rate/exchange_rate_13_10_2026.pdf` (PDF); the date in the file path changes with the sheet. No documented JSON API for this sheet was found. The HTML parser validates the publication date, expected bid/ask table headers, supported rows, numeric values, and response content type. It fails closed on missing or changed layout. This is still page scraping and an upstream markup change can require parser maintenance; it is not represented as a guaranteed stable feed.

The parser and response validator support the currencies shown in the sheet: USD, EUR, GBP, AUD, JPY, CAD, SEK, SGD, CNH, INR, and LKR. Each row is denominated as BDT per one unit of its exact `baseCurrency`; the planner uses the published **ask** and does not invert it. USD retains its distinct direct USD/BDT interbank rate type and weighted-average rate (WAR); the other currencies are labeled Bangladesh Bank cross rates. The UI and rate metadata preserve the currency code and rate type. The source provides CNH (offshore yuan); CNY, KRW, and MYR are not part of the supported currency list or represented as live rates. The source explains USD bid/ask represent previous Dhaka-close interbank rates and cross rates use New York and Dhaka closing rates. Bangladesh Bank says the schedule applies to its purchase/sale transactions with the Government and international organizations, so it is not a student's guaranteed bank or payment-provider rate.

The endpoint returns source name and URL, official publication date, server retrieval timestamp, exact base/quote currency codes, rate type, bid, ask, and USD WAR. It returns a 502 error on upstream failures or malformed data, with no invented fallback. Successful `GET` responses use `Cache-Control: public, max-age=0, s-maxage=86400`, allowing Vercel's CDN to share the validated response for 24 hours while preventing browser-local freshness. The cached body retains the original successful retrieval timestamp and Bangladesh Bank publication date; a cache hit does not rewrite either. After 24 hours, Vercel revalidates on a request. The client reads Vercel's `x-vercel-cache: STALE` state and marks data stale after either five days without a newer official sheet (an application assumption allowing weekends/holidays) or 24 hours without a successful server retrieval. Stale values cannot be applied, and their original dates remain visible. Errors use `no-store`, so malformed or failed upstream responses are not cached. Students can always enter a sourced manual rate; fetching never overwrites it automatically. Static local previews without Vercel's `/api` route will show an API error and retain manual entry.

This uses Vercel's built-in CDN response cache and adds no storage service or package. Vercel caches Function responses by region and may evict them before their TTL; therefore, the 24-hour TTL is a best-effort shared cache per region, not a globally atomic single-fetch guarantee. If a single global cache entry across all regions is required, add a shared remote store such as managed Redis or a Vercel Edge Config write path after approving that infrastructure and its credentials/costs.

The rate is used at full numeric precision and formatted for display only. These are official published reference rates, not executable bank, university, or payment-provider prices. Confirm actual payment terms with the authorized dealer or university-approved provider. Exchange-rate handling does not change the Phase 1 30-day savings contribution schedule.

## Tuition gap and usable funds

- `tuitionBdt = tuition × enteredRate`
- Optional student-entered one-time estimates (visa, applications, flights, insurance, document preparation, accommodation deposit, initial setup, and other one-time costs) are entered in BDT and summed once.
- Optional initial living costs = (`monthlyRent + monthlyFood + monthlyTransport + monthlyUtilities + monthlyOtherLiving`) × the explicitly entered whole-month planning period. If any monthly category is positive, a period is required. Blank fields contribute zero; no cost estimate or period is assumed.
- `requiredFunds = tuitionBdt + payment/transferFees + categorizedOneTimeCosts + initialLivingCosts`
- `usableFunds = max(0, savings − protectedEmergencyFund − committedFunds)`
- `fundingGap = max(0, requiredFunds − usableFunds)`
- `monthlySurplus = monthlyIncome − monthlyLivingCosts`
- A contribution date occurs every 30 full days, starting 30 days from today. Contributions before the first date are not assumed.
- `contributionDates = floor(daysToDeadline ÷ 30)`
- `monthlySavingsTarget = fundingGap ÷ contributionDates` when `contributionDates > 0` and the funding gap is positive; if there is no gap, the target is zero.
- If a positive gap remains but there are no contribution dates before the deadline, the monthly target is unavailable; no monthly contribution can be counted.
- `projectedSavingsCapacity = max(0, monthlySurplus) × contributionDates`
- `projectedShortfall = max(0, fundingGap − projectedSavingsCapacity)`

The expanded study-cost fields are optional BDT estimates entered by the student. The planner shows the BDT totals and, only from the already validated current exchange rate, their destination-currency equivalents (`BDT amount ÷ BDT-per-destination-currency rate`). These equivalents are planning conversions, not provider or university quotes. Blank optional amounts are omitted from the calculation; no cost or living-cost period is invented. A positive monthly living-cost category requires an explicitly entered whole-month period. Existing payment/transfer fees remain distinct from the categorized cost fields to avoid adding one field's total twice.

Deadlines must be real calendar dates in `YYYY-MM-DD` form; impossible dates such as February 30 are rejected. The planner compares local calendar dates, so daylight-saving transitions do not add or remove a deadline day. Today and past dates are rejected. Only complete 30-day intervals count, using `floor(calendarDaysToDeadline ÷ 30)`.

The exact monthly target remains `fundingGap ÷ contributionDates`. For the whole-BDT schedule shown to students, the first `contributionDates − 1` contributions are `floor(fundingGap ÷ contributionDates)` BDT, and the final contribution is rounded up to the remaining gap. This final-cycle adjustment makes the displayed schedule cover the funding gap; it may exceed the exact gap by less than one BDT when the converted tuition produces a fractional BDT amount. The underlying gap is not rounded. The existing payment/transfer fee remains separate from categorized study costs; users must not enter the same cost in more than one field. Quote comparison is separate; do not add quote fees to the profile estimate again. Current monthly expenses still determine contribution capacity; the optional initial living-cost estimate is a separate upfront funding need and is not added again to monthly budget expenses. The deadline projection assumes each full 30-day contribution is made on time and no income, expense, exchange-rate, or fee changes. It is not a guarantee.

The dated contribution roadmap uses the exact adjusted whole-BDT schedule above and assigns cycle `n` the calendar date `startingDate + 30 × n calendar days`; no elapsed-millisecond calculation is used. It displays cumulative planned contributions separately from projected savings balance. Projected balance uses the existing assumption that the full non-negative monthly surplus is saved each cycle (`usableFunds + monthlySavingsCapacity × cycle`); the remaining funding gap is based on that projected balance, not on assuming every required contribution is affordable. The roadmap marks whether the existing projected capacity covers the gap, and each cycle identifies any required contribution amount above the current monthly capacity. Dates and contributions are plans, not guaranteed future payments. A covered gap produces no contribution rows; a positive gap with zero complete cycles produces an explanation and no dated rows.

To keep the page and A4 preview responsive, the dated list displays up to 120 complete 30-day cycles. For a longer horizon, the planner reports the full baseline projection and explains that the dates are not displayed; it does not truncate the underlying financial calculation or imply that the missing rows were generated.

The deadline and calendar summaries use calendar-date differences rather than elapsed milliseconds, so daylight-saving transitions do not change the number of days. Stress tests are independent copies of the baseline input: rate stresses multiply the entered rate by 1.05 or 1.10; an expense stress adds the explicitly supplied monthly expense increase. A missed-contribution stress removes one full 30-day contribution cycle. The assumed missed amount is the whole-BDT scheduled contribution for that cycle (the regular amount, or the final-cycle adjustment when only one cycle is scheduled), capped at the positive monthly surplus available for that cycle. With no contribution dates or no positive surplus, the missed amount is zero. A combined expense-and-missed-contribution case applies both. Each scenario recomputes the gap, target, capacity, and shortfall, and does not mutate the baseline. No expense increase is assumed unless provided.

The downloadable text report and the Student Financial Readiness Report are generated locally in the browser from validated inputs and the existing deterministic results. The A4 report can include available stress results, the rate source and timestamp, and suggested next steps; its preview is reviewed before using the browser print dialog. Neither report is sent to the assistant endpoint. The optional report name is local to the browser and appears only in the generated report.

Each financial input is limited to 1,000,000,000,000 in its entered currency. Calculated BDT values (including converted tuition, required funds, projected funds, and contribution capacity) are also limited to 1,000,000,000,000 BDT. A plan is rejected with a clear validation message if any such result is non-finite or exceeds that ceiling; the app does not display an out-of-range calculation. This ceiling preserves the existing input scale while preventing multiplication or long projection periods from producing unsupported results.

## Quote comparison

Each manually entered quote must provide a provider/name, a recipient currency matching the selected corridor, a positive BDT payment principal in the comparison controls, a total sender cost in BDT that is at least that principal, a positive recipient amount, a quote source/reference, and a valid local timestamp in `YYYY-MM-DDTHH:mm` form. The principal, total sender cost, recipient amount, fee, and quoted rate must be finite and no greater than 1,000,000,000,000; total and recipient amounts must be positive, fees non-negative and no greater than the sender total, and a supplied quoted rate positive. A separately stated fee and quoted rate are optional. Delivery days are optional except for speed ranking. A valid supplied estimate must be a whole number from 0 to 365. A missing or invalid estimate is displayed as “not provided” and does not disqualify a quote from cost or recipient-amount ranking; it does disqualify that quote from speed ranking.

**Freshness rule:** timestamps use the student's device local time because the quote form uses a local date/time input. Future-dated timestamps are rejected. Quotes more than 24 hours old are rejected; a quote exactly 24 hours old is accepted. This 24-hour maximum is a conservative application default (`QUOTE_MAX_AGE_MS`) that can be changed in the finance module. It is not a provider expiry rule; students must still check the provider's stated expiry and terms.

The same quote validation and ranking result feeds the comparison view and the exported report. Only eligible quotes are listed as comparison results in the report; excluded quote entries are listed with their validation reason. A missing delivery estimate excludes a quote only from speed ranking, not from cost or recipient-amount ranking. Quotes are compared only when their recipient currency matches the selected destination currency.

These checks validate the fields the student typed. They do **not** authenticate the source/reference, verify that a provider issued the quote, confirm route availability for the student's institution, or check the fee scope/intermediary charges. A quote passing validation is still a manually entered, unverified quote. Effective rate can be calculated for explanation as `total BDT sender cost ÷ destination-currency recipient amount`, but the application does not independently confirm that rate against the provider.

## Validation

Currency and destination must match one of the supported destinations: USD, EUR, GBP, AUD, JPY, CAD, SEK, SGD, CNH, INR, or LKR, with BDT as the home currency. CNH is kept distinct from CNY. Monetary inputs must be finite, non-negative, within the application safety limit, and tuition/payment principal greater than zero. The rate must be positive and timestamped. Deadlines in the past or today are rejected.

## Multi-page plan state

`lib/plan-state.js` stores the successfully calculated baseline profile under the versioned key `campusbridge.plan.v1` in `sessionStorage`. The browser tab's session is shared across same-origin pages in that tab. The module uses an explicit list of permitted profile fields and revalidates the planning mode, currencies, numeric inputs, dates, calculated BDT ceiling, and deadline through `lib/finance.js` before restoring. Missing, corrupt, future-dated, unsupported-version, or invalid state is treated as unavailable; a valid state is replaced after each successful planner calculation. An invalid/rejected baseline is cleared. Savings are preserved as other-savings amount plus an array of unlabelled manual account balances; manual account labels and the optional report-only name are not persisted.

When present, saved stress results are a separately allowlisted list of bounded numeric outputs generated by the deterministic finance module. They are replaced when the baseline is recalculated. No API key, token, uploaded document, or student name belongs in this state. Session storage is not encrypted; scripts on this origin can access it, and it is not an account backup. Clear Plan removes the current tab's saved plan after confirmation.
