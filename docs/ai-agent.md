# Assistant behavior

## Two answer paths

The planner and feature pages use deterministic local calculations for funding gaps, contribution targets, budgets, and quote comparisons. The shared `lib/assistant-task.js` routes supported funding, savings, budget, rate-provenance, and quote-comparison requests to those existing finance functions. It uses the validated current plan on the planner or the recalculated plan saved for the current browser tab on the Assistant page. Missing or invalid plan data prompts the user to complete the planner; it is not filled in by the model. Quote comparisons use only entries accepted by `Finance.compareEnteredQuotes` and are labeled student-entered and unverified. A saved rate response displays its saved source and timestamp and does not claim that the rate is still current.

For general questions not handled locally, the browser sends the current `{ question }` and, only for a saved signed-in conversation, its conversation ID and current saved user-message ID to `/api/assistant`. It never sends prior message text. The endpoint verifies the Supabase access token and conversation ownership under the user's JWT and existing RLS policies. It confirms the referenced user message is the latest user message in that conversation and matches the current question. The endpoint sends only that current question once to Groq. Because arbitrary natural-language messages cannot be reliably classified as free of sensitive information, saved conversation messages are not used as model context. Saved plans, balances, report data, quotes, and other database records are not loaded as context. Signed-out chat remains temporary and sends only the current question. See [security and data handling](security-report.md).

The remote endpoint is hosted in `api/assistant.js` and calls Groq's OpenAI-compatible API. The default model is `openai/gpt-oss-20b`; `GROQ_MODEL` may override it. The Groq API key comes from the server environment as `GROQ_API_KEY` and is never included in browser code or stored plan state. Saved-conversation ownership verification additionally requires server-side `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`; the route never uses a service-role key. The endpoint accepts only a question and optional verified saved-message references, validates JSON, applies a 1,000-character question limit and 4 KB body limit, requests at most 4,096 completion tokens, returns at most 16,000 characters, and uses a 30-second SDK timeout. Output-limit and server-cap conditions are marked incomplete for the client. Provider errors returned to clients are generic.

The system instructions request direct, accurate answers in natural English, with detail matched to the question. They discourage filler and excessive formatting, require uncertainty to be stated, prohibit invented rates or payment offers, and direct personal financial calculations back to the deterministic planner. Answers are educational, not personalized financial advice. Markdown is rendered with safe DOM operations; model HTML is not executed and only safe HTTP(S) links are allowed.

If a key is missing, saved-conversation verification fails, or the provider fails, the endpoint returns a safe error and the UI continues to offer local planning. Do not log prompts or responses, pass financial plans or quote data as context, or expose credentials in source files.

## Operations

Set `GROQ_API_KEY`, `SUPABASE_URL`, and `SUPABASE_PUBLISHABLE_KEY` as server environment variables in Vercel or a local ignored `.env.local` file. `GROQ_MODEL` is optional. The publishable key is passed only between the server and Supabase; never configure a service-role or secret key for this feature. The endpoint's in-memory per-IP limiter is instance-local and does not provide global abuse protection. Provider access, account limits, and model availability depend on the Groq account configuration.

For a signed-in user, the browser saves the submitted question and displayed answer in `assistant_conversations` and `assistant_messages` through the existing Supabase client. For remote questions in a saved conversation, the server verifies the access token with Supabase Auth, checks conversation ownership and verifies that the referenced current user message is still latest. It does not read prior message text. This requires the existing chat tables and policies plus the three server environment variables above. The migration's application to any live project is unverified. Signed-out chats remain page-local.
