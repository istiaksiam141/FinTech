# Assistant behavior

## Two answer paths

The planner and feature pages use deterministic local calculations for funding gaps, contribution targets, budgets, and quote comparisons. The shared `lib/assistant-task.js` routes supported funding, savings, budget, rate-provenance, and quote-comparison requests to those existing finance functions only when the question clearly asks for an explanation, calculation, estimate, comparison, or plan action. A plain statement such as “My university tuition is 5000 USD” is not treated as a request to calculate from the saved plan. It uses the validated current plan on the planner or the recalculated plan saved for the current browser tab on the Assistant page. Missing or invalid plan data prompts the user to complete the planner; it is not filled in by the model. Quote comparisons use only entries accepted by `Finance.compareEnteredQuotes` and are labeled student-entered and unverified. A saved rate response displays its saved source and timestamp and does not claim that the rate is still current.

The browser sends the current `{ question, planContext }` to `/api/assistant`. `planContext` is a bounded, allowlisted summary of deterministic cost/funding results, dated schedule, rate provenance, linked savings-tracker aggregates, and currently eligible entered quote comparisons. It excludes full profile fields, account details, deposit notes, and quote references. The server validates the object shape, types, numeric limits, item counts, and byte size; context strings remain untrusted data. The AI may explain and assess the supplied figures but must not replace the deterministic calculations. A visible, unchecked-by-default option lets a signed-in user additionally consent to including recent messages from that same saved chat. When enabled, the server verifies the Supabase access token, conversation ownership under the user's JWT and existing RLS policies, and that the referenced current user message is latest and matches the question. It then loads prior user and assistant messages itself; browser-supplied message history is never accepted. Context is kept in chronological order and limited to 11 earlier messages plus the current message and 6,000 total characters. Context retrieval failures stop the request safely. Consented history may contain sensitive details, so the user sees a disclosure before enabling it. Saved database plans and other database records are never loaded as context. Signed-out chat remains temporary. See [security and data handling](security-report.md).

The remote endpoint is hosted in `api/assistant.js` and calls Groq's OpenAI-compatible API. The default model is `openai/gpt-oss-20b`; `GROQ_MODEL` may override it. The Groq API key comes from the server environment as `GROQ_API_KEY` and is never included in browser code or stored plan state. Saved-conversation ownership verification additionally requires server-side `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`; the route never uses a service-role key. The endpoint accepts a question, an optional bounded plan summary, a boolean history-consent flag, and optional verified saved-message references; it validates JSON, applies a 1,000-character question limit, a 12 KB plan-summary cap and 16 KB total body cap, requests at most 4,096 completion tokens, returns at most 16,000 characters, and uses a 30-second SDK timeout. Output-limit and server-cap conditions are marked incomplete for the client. Provider errors returned to clients are generic; safe server diagnostics include vetted status and error codes only.

The system instructions request direct, accurate answers in natural English, with detail matched to the question. They discourage filler and excessive formatting, require uncertainty to be stated, prohibit invented rates or payment offers, and direct personal financial calculations back to the deterministic planner. Answers are educational, not personalized financial advice. Markdown is rendered with safe DOM operations; model HTML is not executed and only safe HTTP(S) links are allowed.

If a key is missing, saved-conversation verification fails, or the provider fails, the endpoint returns a safe error and the UI continues to offer deterministic local guidance. Do not log prompts or responses or expose credentials in source files.

## Operations

Set `GROQ_API_KEY`, `SUPABASE_URL`, and `SUPABASE_PUBLISHABLE_KEY` as server environment variables in Vercel or a local ignored `.env.local` file. `GROQ_MODEL` is optional. The publishable key is passed only between the server and Supabase; never configure a service-role or secret key for this feature. The endpoint's in-memory per-IP limiter is instance-local and does not provide global abuse protection. Provider access, account limits, and model availability depend on the Groq account configuration.

For a signed-in user, the browser saves the submitted question and displayed answer in `assistant_conversations` and `assistant_messages` through the existing Supabase client. For remote questions in a saved conversation, the server verifies the access token with Supabase Auth, checks conversation ownership and verifies that the referenced current user message is still latest. It loads prior messages only when the user enables the visible history option; otherwise no history query is made. Existing RLS and owner filters apply to every query. This requires the existing chat tables and policies plus the three server environment variables above. No schema change is required. The migration's application to any live project is unverified. Signed-out chats remain page-local and current-question-only.
